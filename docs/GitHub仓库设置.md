# GitHub 仓库设置与落地顺序

本页用于仓库管理员操作。当前本地仓库只有 `main` 和两次提交，尚无根目录的 CI 工作流；先从简单的 PR 审查规则开始。

## 第一步：确认仓库与负责人

本地 `origin` 当前指向 `Yu20040207/Four-wheel-robot`。确认它是否为公司团队最终协作的仓库，以及谁有仓库管理权限。填写[模块责任表](模块责任表.md)中的负责人、GitHub 账号或组织团队和备份审阅人；本人不能审阅自己的 PR，因此每个模块需要可用的备份审阅人。

GitHub 组织团队用于 `CODEOWNERS` 时，需要是可见团队并对仓库有写入权限。负责人未定时，先用 PR 模板手动邀请审阅，不要提交只有空白负责人的 `CODEOWNERS`。

## 第二步：保护 `main`

在仓库 **Settings → Rules → Rulesets** 中为默认分支 `main` 建立分支规则集，并设为启用：

1. 要求通过 Pull Request 才能合并。
2. 要求至少 1 人批准；建议新提交后使旧批准失效。
3. 阻止强推和删除分支；仅给确有需要的管理员保留绕过权限。
4. 在 **Settings → General → Pull Requests** 允许 **Squash merging**。团队统一用这个合并方式，以 PR 标题作为 `main` 中的提交说明。

目前没有根目录的持续集成检查，先不要把不存在的检查设为必需。等各模块有稳定的编译或测试任务后，再逐项设为必需检查。

## 第三步：启用自动负责人审阅

负责人账号确认后，在根目录的 `.github/CODEOWNERS` 按[责任表](模块责任表.md)为各模块路径分配实际 GitHub 账号或团队。此文件必须位于 PR 的目标分支中才会自动请求审阅。检查 GitHub PR 页面是否显示正确的 code owner；确认后在 `main` 的规则集中开启要求 code owner 审阅。

## 第四步：分批清理历史包袱

1. 先轮换当前已提交配置文件中的密码与密钥，改用本地配置或安全的部署方式；仅把文件加入 `.gitignore` 无法从旧提交删除凭据。
2. 在独立 PR 中确认并停止追踪 Keil 用户状态、编译输出、刷机工具临时文件、日志和编辑器恢复文件。`.gitignore` 只防止以后误加，已追踪文件仍会出现在提交中。
3. 由模块负责人确认 `materials/` 与 `code/Program/` 的重复工程，保留一个明确的维护入口，并说明历史资料的存放方式。
4. 大型压缩包和模型文件按用途决定保留位置。需要缩减已有 Git 历史时，先制定团队迁移计划；历史改写会影响所有协作者的克隆和分支。

以上步骤分别提交，避免把协作规则、凭据迁移和大量文件清理混在同一个 PR 中。
